# Rollback and the database schema

A relay rollback reverts the code and the image. It never reverts the database schema. This page says why, which `prisma/schema.prisma` changes survive a rollback, and what to do when one does not.

## Why a rollback leaves the schema alone

The deploy hook in `.relay.yml` applies the schema in `post_update`: it runs `docker compose -f docker-compose.traefik.yml run --rm -T --build migrate`. The `migrate` service runs `prisma/pre-push/advisory-unique-key.sql` and then `prisma db push` (see `docker-compose.traefik.yml`). The repository has no `prisma/migrations` directory (see [Architecture](architecture.md)), so there is no migration history and no down step to run. `.relay.yml` also sets `rollback: true`. When the relay rolls back, the new schema is already committed; the old code and image come back on top of it.

So after a rollback the instance runs the old release against the new schema. That state is only healthy when the old code works with the new schema.

## Expand and contract for `prisma/schema.prisma`

Make every schema change safe for the release before it, and remove things only in a later release.

Safe across a rollback (additive):

- a new table;
- a new optional column (`String?`), or a required column with a database-level default (a static value, `now()`, `autoincrement()`); `cuid()` and `uuid()` defaults are generated by Prisma Client, not by the database, so old code inserting rows does not get them;
- a new index that is not unique.

Not safe across a rollback:

- a dropped or renamed column or table (old code queries what no longer exists; `prisma db push` also refuses a drop that loses data unless `--accept-data-loss` is passed, and the `migrate` command carries no such flag);
- a new `NOT NULL` column without a database-level default, including one whose only default is `@default(cuid())` or `@default(uuid())` (old code inserts rows without it);
- a type change on an existing column, or a change from optional to required (`String?` to `String`); the opposite direction, required to optional, is safe;
- a new unique key or unique index that old code can violate (old code fails with `P2002`);
- a removed enum value, and a new enum value once rows hold it (old code cannot read those rows).

For a change in the second list, split it over releases: first ship the additive step (new column optional, old column kept) together with code that works against both shapes, then in a later release tighten or drop. A rollback of the later release then lands on a schema the earlier code still understands.

## Runbook: a rollback after a non-additive schema change

Symptoms: the relay rolled back (or you rolled back by hand), and the old release fails against the new schema, for example with `P2002` or with a missing column.

1. **Decide: forward fix or restore.** Prefer the forward fix. Choose restore only when the new schema damaged data or no quick code fix exists, because a restore loses every row written after the dump.
2. **Forward fix.** Fix the code so it works with the new schema, merge it, and deploy as usual (see [Deployment](ways-of-working.md#deployment)). Do not simply revert a commit that added a column or table: the revert makes `prisma db push` drop it; when the column or table holds rows, that is a data-loss push which the `migrate` command refuses (it passes no `--accept-data-loss`), so the deploy stops. Revert the code that needs the new shape, and leave the schema line in place until a deliberate contract release.
3. **Restore from a backup.** Take a dump of the current state first if you want to keep it (`scripts/restore.sh` does this itself unless you pass `--no-pre-backup`). Check out the release you want to run, because the `migrate` step builds from the working tree. Then run `scripts/restore.sh --yes <dump.sql>` with the dump taken before the deploy (`ls -t backups/depsight-*.sql | head -3`). What it does, its exit codes and the limits of a dump are in the Restore paragraph of [Backup and restore](configuration.md#backup-and-restore); they are not repeated here. The script does not read the dump's SQL. Before it touches anything it refuses a dump that is under 1 KiB or lacks the `-- PostgreSQL database dump complete` marker (a truncated dump), and a dump with damage it can see in the bytes: a NUL byte, a `\restrict` / `\unrestrict` line pair that is not exactly the one `pg_dump` 16.10 and later writes, or a number of `COPY ... FROM stdin;` lines that differs from the number of lines that end COPY data (a psql in the `db` service that is not 16.10+, 17.6+ or 18+ is refused too, with exit 2). A dump made with `--data-only` or `--create` is refused as well. So the `END;` line that closes a plpgsql function body or a `BEGIN ATOMIC` SQL function body no longer refuses a dump, and neither does a transaction control keyword or a psql backslash command that only sits in a string, a comment or COPY data. What such a line does when it is real SQL is caught while the dump loads: psql runs it in restricted mode under a key the script draws at random, so every psql meta-command in the dump is an error; a check after the dump fails when `txid_current()` has changed, that is when the dump ended the transaction; a second check fails unless psql ran as many COPY commands as the dump has `COPY ... FROM stdin;` lines; and the load counts only when psql exits 0 and prints the token the script echoes after its `COMMIT`. The dump is loaded into a scratch database first, so a dump that fails any of this is refused before the app is stopped and the database keeps its content. The checks, the dumps they refuse as a false positive (a line that is exactly `\.` or in the COPY form inside a string, a comment or a function body, or a COPY that `pg_dump` does not write) and why none of this is a security boundary are in the "How a load stays one transaction" and "Not a security boundary" paragraphs of [Backup and restore](configuration.md#backup-and-restore).
4. **Check.** `curl -fsS https://depsight.opentriologue.ai/api/health` answers, and a CVE scan of a repository completes.

### Worked example: the Advisory unique key

`Advisory` carries a unique key over `(scanId, ghsaId, packageName)`, created by `prisma/pre-push/advisory-unique-key.sql` during `post_update`. The key stays in place after a rollback. Releases from before the key do not collapse repeated Dependabot alerts, so their CVE scans of repositories with repeated alerts fail with `P2002` until the next forward deploy.

- Forward fix: deploy a release that carries the key (the normal path).
- Intentional downgrade: drop the index first, with the command the stack's other `psql` recipes use:

  ```bash
  docker compose -f docker-compose.traefik.yml exec -T db psql -v ON_ERROR_STOP=1 -U depsight -d depsight \
    -c 'DROP INDEX "Advisory_scanId_ghsaId_packageName_key";'
  ```

  The next deploy of a release with the key recreates it through the same SQL step. Background in [Deploying the Advisory unique key](configuration.md#deploying-the-advisory-unique-key).

### Worked example: hashed API tokens

The same pre-push SQL file hashes `ApiToken.token` in place (lowercase hex SHA-256 of the `dsat_` token; rows that still start with `dsat_` are the ones not yet migrated, so a re-run changes nothing). The schema did not change, so `db push` has nothing to do for it, but the data did, and the old release matches tokens by their raw value. After a rollback to a release from before the hashing, every `dsat_` token answers 401, existing ones included. The hashes cannot be turned back into tokens.

- Forward fix: deploy a release that hashes (the normal path); the tokens keep working. This is also the fix after an automatic relay rollback that happened after the migrate step (a failed `prisma db push` or health check): the tokens answer 401 only until that forward deploy, nothing needs re-issuing.
- The deploy that introduces hashing has no 401 window: until the pre-push step has run, the new code also finds a row that still holds the raw value.
- Intentional downgrade: re-issue the tokens afterwards (Settings, or `scripts/mint-api-token.ts`) and update the agents that use them.

## Checklist for a pull request that touches `prisma/schema.prisma`

- The change is additive, or it is split into an expand release and a later contract release.
- The previous release still runs against the new schema (old code, new schema), or the pull request says why it cannot.
- A fresh dump exists before the merge: `make backup` (`scripts/backup.sh`).
- A new unique key over existing rows has its step in `prisma/pre-push/`.
