## One shared shape, five dedicated files, one inline fallback

`DependencyInfo` (`lib/deps/age-checker.ts:23-33#"latestPublishedAt: Date"`) is the return shape every ecosystem scanner produces. Five non-npm ecosystems each ship a dedicated file exporting the identical signature `scan<Eco>Deps(accessToken: string, owner: string, repo: string, manifestPaths: string[] = []): Promise<DependencyInfo[]>` (`lib/deps/go.ts:91#"export async function scanGoDeps("`, `lib/deps/java.ts:89#"export async function scanJavaDeps("`, `lib/deps/php.ts:75#"export async function scanPhpDeps("`, `lib/deps/python.ts:63#"export async function scanPythonDeps("`, `lib/deps/rust.ts:64#"export async function scanRustDeps("`), each backed by its own registry (Go proxy, Maven, Packagist, PyPI, crates.io respectively). `analyzeDepAge` dispatches to the matching one by detected ecosystem (`lib/deps/age-checker.ts:151-155#"if (ecosystemInfo.ecosystem === 'php') return"`). npm has no equivalent file: it is the fallback branch inlined directly in `age-checker.ts` (`lib/deps/age-checker.ts:157-241#"return buildResult(deps);"`), which reads manifests via `fetchNpmManifests`/`unionNpmDeps` (`lib/manifest-discovery.ts:1232#"export async function fetchNpmManifests("`, `lib/manifest-discovery.ts:273#"export function unionNpmDeps(manifests:"`) and queries the npm registry directly rather than delegating to a per-ecosystem module.

The npm row's `installedVersion` is the manifest floor (the unioned spec with its leading range operator stripped, `^7.3.5` gives `7.3.5`, `^8` gives `8`), raised only where the CVE channel's narrow proof holds. `analyzeDepAge` passes the manifests it already read to `collectNpmReportVersions` (`lib/cve/osv.ts:666#"export async function collectNpmReportVersions("`), which runs the same npm resolution as the CVE channel (`collectNpmEntries`, shared with `collectDeps`) and returns, per unioned package name, `{ strip, raisedTo }`. `strip` is today's floor strip. `raisedTo` is set when the name has a usable floor (`manifestFloor`, the same floor the CVE chain falls back to), a version the spec admits for any valid range (an upper-bound spec such as `<2.0.0` takes `semver.minVersion`, not its stripped bound), no manifest the scan read declares the name in `optionalDependencies`, `peerDependencies` (marked optional or not) or `bundleDependencies` / `bundledDependencies` (`declaredOutsideDeps`, which resolves an `npm:` alias to its target), the report's reading of the narrow proof holds (`narrow.dropSafeForReport(name, floor)`, selected by `collectNpmReportVersions`' `overridesDoNotBlock` option, which `analyzeDepAge` sets: every manifest declaring the name is proven by the `package-lock.json` that installs it, its own or for an npm workspace member the root's whose entries prove the membership, every manifest of the scan is locked, no lockfile installs the floor, and the tree, `.npmrc`, `packageManager` and foreign-lockfile conditions hold; the CVE channel asks `narrow.dropSafe(name, floor)` instead, the same proof read more strictly about `overrides`, see below) and the narrow resolution added at least one version for the name; it is then the lowest addition in semver order, unless that is below the floor, in which case the floor strip stays. Each addition is the top-level version a declaring project's own `package-lock.json` (for a workspace root or member, the root's) installs for its `dependencies` or `devDependencies` declaration; a copy installed only as a dependency of another package (nested, or hoisted in a project that does not declare it) is not reflected in the row, though the proof sees it (a copy of the floor anywhere keeps the floor). `resolveNpmReportVersions` (`lib/deps/age-checker.ts:271#"async function resolveNpmReportVersions("`) maps the names to those rows, and the row shows `raisedTo ?? strip` (`lib/deps/age-checker.ts:206#"const cleanInstalled = reportedVersion("`). So the row rises above the manifest floor only where every declaration of the package is in `dependencies` or `devDependencies` and every declaring project's lockfile proves a higher version (vite 7.3.7 in `frontend/` and 8.3.5 in `backend/` with spec `^7.3.5` gives 7.3.7; 9.1.5 is lower than 10.0.1; in a workspace whose members all resolve the root lockfile's vite 7.3.7, spec `^7.0.0` gives 7.3.7). `overrides` do not keep the floor for the report, which differs from the CVE channel: `dropSafe` counts a workspace member with any `overrides` (npm applies the root's only) and a root or standalone manifest whose `overrides` are not all plain string ranges (a nested object such as `next: { postcss: ^8.5.18 }`, a `$` reference, a version selector) as not locked, so one such entry in a repository kept every row at the floor. `dropSafeForReport` ignores a member's `overrides` and accepts any shape at a root or standalone manifest. The report also reads a project nested below a workspaces root as standalone (`lib/manifest-discovery.ts:2434#"const reportGovernanceOf = (m: NarrowManifest): Governance => {"`, the deploy-panel shape: `mcp/` with a `package-lock.json` of its own beside the workspaces `backend` and `frontend`, which the strict reading leaves unknown and which kept every name of the repository at the floor). A manifest below exactly one `workspaces` root that the strict reading leaves unknown is installed by its own lockfile when that root's lockfile proves membership at all (the same proof as for a member), has no entry for the manifest's folder or below it (no member, no link, no install under it, compared in lower case; the walk over a lockfile key stops at the bounds a member folder has, `MAX_MEMBER_FOLDER_SEGMENTS` segments and `MAX_MEMBER_FOLDER_CHARS` characters, so one very long key costs a constant, `addClaimedFolders`), and the manifest has an own `package-lock.json` of version 2 or 3 that was read and parses. The workspace patterns are never evaluated. Such a manifest counts for the report's every-manifest-locked and every-declarer-narrow conditions, and the lowest-version rule reads `narrow.additionsForReport`, the CVE channel's `additions` plus the versions of those nested manifests (the CVE list itself is unchanged; the report list is a getter built on the first read, and is `additions` itself when no manifest is strictly unknown, so the CVE scan never pays for it), so a name declared in both the workspace and the nested project shows the lowest of the lockfiles' versions. Measured with bounded real runs (npm 10.9.2 and 11.21.1): root `npm ci` leaves a folder the patterns do not match alone and `npm ci` inside it installs its own lockfile (also for a folder a negated pattern excludes); a folder the patterns match while the root lockfile lacks it is refused by `npm ci` at the root and inside the folder (exit 1, `Missing: <name> from lock file`), so nothing is installed from a lockfile that disagrees with the row. A folder the root lockfile links stays a member, whose installing lockfile is the root's and not its own; a missing, unparsed or version 1 own lockfile, a root lockfile that records other `workspaces` than the root `package.json`, an unread `package.json` above, or a second `workspaces` root above keep the manifest unknown and the floors. The row is the top-level lockfile entry of a declared dependency, so it is never above what `npm ci` installs: when `npm ci` accepts the lockfile it installs exactly those entries (measured with npm 10.9.2 and 11.21.1: a workspace root's `overrides` of TRANSITIVE dependencies are not enforced against the lockfile (`npm ci` exits 0 and installs the lockfile), a root override of a workspace member's DIRECT dependency is accepted by 10.9.2 but refused by 11.21.1 (`npm ci` exit 1), and a member's own `overrides` are ignored by both), and when it refuses the lockfile (a standalone project whose lockfile does not reflect its `overrides`) nothing is installed from it. As a conservative choice it checks what it can see: a plain top-level override entry (a package name with a non-empty semver-range string) that some lockfile entry of that name does not satisfy keeps the floor, because an `npm install` would re-resolve to the override. Every entry is looked at, not only those before the first non-plain one. Every other condition of the proof still applies to the report beside `overrides`: a copy of the floor installed anywhere, a declaring project without a lockfile of its own, a `.npmrc`, a foreign lockfile, `packageManager`. Yarn-only repositories (the proof reads `package-lock.json` only), lockfileVersion 1, a workspace whose root lockfile does not prove the membership, a copy under a workspace member's own folder, an `npm:` alias, an unreadable or malformed lockfile, a `.npmrc`, a declaring project without a lockfile of its own and a spec with no usable floor (`latest`) keep the floor strip, and a project without a lockfile never takes the version of another project's lockfile. The row is raised only from `dependencies` and `devDependencies` declarations; an optional, peer or bundled declaration keeps the floor, even where the CVE scan adds its version as a query (a project with vite as a peer dependency locked at 7.3.6 beside one with it in `dependencies` locked at 7.3.7 shows 7.3.5, not 7.3.7). The registry lookup then takes `publishedAt`, `ageInDays` and the status for the shown version, compared with semver (`classifyStatus`, `lib/deps/age-checker.ts:115#"export function classifyStatus("`: a partial numeric floor strip such as `8` or `7.3.5 <8` is read as its first version, a strip whose first token (split on whitespace or `|`) is itself a full version, such as the prerelease floor strip `1.0.0-beta.1 <2` (shown for `>=1.0.0-beta.1 <2`), is read as that token, a shown string that is no version, such as the digits left of a git or URL spec (`2#main`), has status UNKNOWN, a prerelease sorts below its release, an installed version ahead of the latest is up to date) against the latest version. A row is DEPRECATED when the packument's `versions` entry for the shown version carries a non-empty `deprecated` string: npm's deprecation message lives per version of the shown version (a full packument has no top-level `deprecated` field), and an empty message, a version entry without the key, or a shown version that is not an exact key of `versions` (a partial strip such as `8`) is not deprecated. The latest version is `dist-tags.latest`; when that tag is a prerelease (a package can publish its next major as a release candidate under `latest`) it is the highest non-prerelease version among the packument's `versions` keys (the `time` keys only when the packument has no `versions` map, because `time` keeps unpublished versions and holds `created` and `modified`), and the tag stays when the packument has no stable version or the tag is not a semver version (`pickLatestVersion`, `lib/deps/age-checker.ts:68#"export function pickLatestVersion("`); `latestPublishedAt` is the publish time of the chosen version; a shown version missing from the registry's `time` map gives `ageInDays: -1` and no `publishedAt`, while `installedVersion` and the status still come from the shown version. A failed resolution leaves every name at the floor strip and is reported as a degraded source, as is an unreadable lockfile. The extra GitHub requests over the report before it read lockfiles are the lockfile reads (the `package-lock.json` and `yarn.lock` files of the manifests' directories, only the observed ones when the git-tree walk was complete); the manifests are not read twice. The CVE channel's query sets are unchanged.

## The `-1` sentinel never reaches the database as `-1`

Every scanner, the five dedicated files and the inline npm branch alike, uses `ageInDays: -1` to mean "publish date unknown or unresolved": `lib/deps/go.ts:83#"ageInDays: -1,"`, `lib/deps/java.ts:58#"ageInDays: -1,"` and `lib/deps/java.ts:86#"return { publishedAt: null, ageInDays: -1 };"`, `lib/deps/php.ts:63#"ageInDays: -1,"`, `lib/deps/python.ts:50#"ageInDays: -1,"`, `lib/deps/rust.ts:52#"ageInDays: -1,"`, and the inline npm branch's own default (`lib/deps/age-checker.ts:312#"ageInDays: -1,"`) and computed case (`lib/deps/age-checker.ts:217-219#": -1;"`, `installedPublishedAt ? Math.floor(...) : -1`). But `lib/deps/scanner.ts:50#"ageInDays: d.ageInDays >= 0 ? d.ageInDays : null,"` rewrites that sentinel before the `Dependency.createMany` write: `ageInDays: d.ageInDays >= 0 ? d.ageInDays : null`. Every persisted `Dependency` row therefore has `ageInDays` as either a real day count or `null`, never `-1`.

`prisma/schema.prisma:188#"null = unknown"`'s field comment reads `ageInDays Int? // null = unknown (the scanner maps its -1 sentinel to null before writing)`, so it states what the column holds while naming the in-memory `-1` convention that exists only above the write path. A query for `ageInDays = -1` finds nothing because the "unknown" case is always stored as `null`. `lib/deps/scanner.ts:43#"await tx.dependency.createMany({"` (`Dependency.createMany`) is the only write path for `Dependency` rows in the codebase (an `rg` for `dependency.create`, `upsert` and `update` finds no other), and the readers (`app/api/deps/route.ts:122#"ageInDays: d.ageInDays,"`, `lib/export/repo-bundle.ts:259#"ageInDays: dependency.ageInDays,"`, `lib/sbom/cyclonedx.ts:173#"if (dep.ageInDays !== null) {"`, the dashboard components) all treat `null` as unknown.

## The age check tests for null only

`lib/policy/engine.ts:274#".filter((d) => d.ageInDays !== null && d.ageInDays >"`'s `DEPENDENCY_MAX_AGE` filter reads `d.ageInDays !== null && d.ageInDays > maxAgeDays`. Because every persisted unknown age is `null`, the check needs no `-1` clause and an unknown age never triggers the policy. `tests/policy/engine.test.ts` covers this with `null` fixtures, including a case with a negative `maxAgeDays` (the write-time validator accepts any finite number), where a `!== -1`-only check would flag the unknown dependency because `null > -1` is true in JavaScript.
