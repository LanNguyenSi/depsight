The "Security model" section of `docs/architecture.md` lists the credentials and how each is stored, and `docs/api.md` lists which endpoints accept a Bearer token. This doc connects the files that resolve a caller, hold a secret, or reach an outside system.

## Who a request acts as

GitHub sign-in requests the scopes `repo user:email read:org` (`lib/auth.ts:16-18#"scope: 'repo user:email read:org',"`) and writes the returned access token onto the `User` row at every sign-in (`lib/auth.ts:79-84#"githubToken: account.access_token ?? '',"`). The session callback reads the row again for each session and puts only its id and login into the session (`lib/auth.ts:107-117#"session.user.githubLogin = dbUser.githubLogin;"`); the GitHub token is deliberately not part of it, because with JWT sessions that object is what `GET /api/auth/session` returns to the browser. Server code reads the token from the `User` row with `getSessionGitHubToken` (`lib/auth-api.ts:29-34#"return row?.githubToken ?? '';"`).

`resolveRequestUser` decides the caller of every route that accepts a Bearer token:

- A session user resolves first and always gets `WRITE` (`lib/auth-api.ts:49-60#"scope: 'WRITE',"`), with the token read from its `User` row by `getSessionGitHubToken`.
- Otherwise an `Authorization: Bearer dsat_...` header is hashed with SHA-256 and the digest is looked up in `ApiToken.token` (a value without the `dsat_` prefix is refused before any lookup); when the digest finds nothing, a second lookup by the raw value finds a row the pre-push step has not hashed yet (a digest never starts with `dsat_`, so this cannot match a hashed row), and a revoked token resolves to nobody (`lib/auth-api.ts:72-89#"if (!record || record.revokedAt) return null;"`). The token resolves to its owner, the owner's GitHub token and the token's own scope (`lib/auth-api.ts:100-105#"scope: record.scope,"`).

A write route checks `hasWriteScope` (`lib/auth-api.ts:18-19#"return user.scope === 'WRITE';"`) and answers a `READ` token with `403`, for example `POST /api/scan` (`app/api/scan/route.ts:22-23#"return NextResponse.json({ error: 'This token does not have write access' }, { status: 403 });"`). Whatever the scope, the token caller's GitHub requests use the owner's stored OAuth token; `GET /api/repos`, open to `READ` tokens, lists repositories from GitHub with it (`app/api/repos/route.ts:19-24#"const allRepos = await getUserRepos(user.githubToken);"`).

Routes that call `auth()` instead of `resolveRequestUser` are session-only; those that need GitHub (`/api/export` when it runs scans, `/api/pr-scan`, `/api/repos/sync`, `/api/dependabot` and its `check` and `enable-all` siblings) call `getSessionGitHubToken` with the session's user id. Token management is one of them on purpose, so a `dsat_` token cannot mint, list or revoke tokens (`app/api/tokens/route.ts:11-13#"revoke tokens, otherwise a leaked token could escalate into more tokens."`).

## API tokens

`POST /api/tokens` mints `dsat_` plus 32 random bytes in hex, stores only its SHA-256 (`lib/api-token.ts`) in `ApiToken.token` and returns the raw value once (`app/api/tokens/route.ts:103-104#"return NextResponse.json({ token: rawToken, record }, { status: 201 });"`). Without a `scope` in the body the token is `WRITE` (`app/api/tokens/route.ts:75-80#"scope = body.scope as ApiTokenScope;"`). `GET /api/tokens` returns metadata only (`app/api/tokens/route.ts:23-30#"revokedAt: true,"`), and `DELETE /api/tokens/[id]` sets `revokedAt` on a token of the caller (`app/api/tokens/[id]/route.ts:22-24#"data: { revokedAt: new Date() },"`). The operator script `scripts/mint-api-token.ts` writes the same kind of row for any user id, also `WRITE` by default (`scripts/mint-api-token.ts:47#"let resolvedScope: ApiTokenScope = ApiTokenScope.WRITE;"`, `scripts/mint-api-token.ts:65-75#"select: { id: true, name: true, scope: true, createdAt: true },"`). The model has no expiry column (`prisma/schema.prisma:241-244#"@default(now())"`): a token works until it is revoked.

## Where the stored GitHub token is used

The `User.githubToken` column (`prisma/schema.prisma:18#"stored in plaintext"`) is also read straight from the database, not from a request's caller, in three places:

- the auto-scan cron, for every user whose token is not empty, to sync repositories and run the three scanners (`lib/cron/auto-scan.ts:54-62#"const githubRepos = await getUserRepos(user.githubToken);"`);
- the PR-scan webhook, for the owner of the tracking row that verified the delivery (`app/api/webhooks/github/route.ts:348-366#"user: { select: { githubToken: true } },"`);
- CI ingestion, for the owner of the repository row (`lib/ci/ingest.ts:24-31#"const token = repo.user.githubToken;"`).

Only sign-in writes the column: the GitHub sign-in callback, and Dev Login when it creates a user (see below). Signing out does not clear it, so the cron, the webhook and CI ingestion keep using the stored token after the user has signed out.

## Secrets at rest

| Value | Column | At rest | Read by |
| --- | --- | --- | --- |
| GitHub OAuth token | `User.githubToken` (`prisma/schema.prisma:18#"stored in plaintext"`) | plaintext | `resolveRequestUser`, `getSessionGitHubToken` (session-only routes) and the three uses above; never the session object |
| `dsat_` API token | `ApiToken.token` (`prisma/schema.prisma:231-234#"@unique"`) | SHA-256 hash (lowercase hex), unique, matched by the digest of the presented token; rows from before the hashing are converted in place by `prisma/pre-push/advisory-unique-key.sql` | `resolveRequestUser`; the raw value exists only in the response that minted it (or the output of `scripts/mint-api-token.ts`) |
| Outgoing webhook signing secret | `WebhookConfig.secret` (`prisma/schema.prisma:293#"// HMAC signing secret"`) | plaintext | the webhook delivery; write-only, no route returns it |
| Slack incoming webhook URL | `SlackConfig.webhookUrl` (`prisma/schema.prisma:307#"// Slack incoming webhook URL"`) | plaintext | the Slack delivery; also returned by `GET /api/slack` and `POST /api/slack` |
| PR-scan webhook secret | `Repo.webhookSecretEnc` (`prisma/schema.prisma:46-48#"webhookSecretEnc"`) | sealed (AES-256-GCM) | the PR-scan webhook route; `GET /api/webhook-secrets` also opens it to report `usable`, without returning it (`app/api/webhook-secrets/route.ts:52#"usable: row.webhookSecretEnc !== null && openWebhookSecret(row.webhookSecretEnc, row.id) !== null,"`); the plaintext is shown only when it is minted |

The outgoing webhook secret is the HMAC key of the `X-depsight-Signature` header (`lib/alerts/notifier.ts:64-78#"headers['X-depsight-Signature'] = signPayload(secret, body);"`). `GET /api/webhooks`, `POST /api/webhooks` and `PATCH /api/webhooks/[id]` all return the row through one select without it (`app/api/webhooks/route.ts:18-25#"const WEBHOOK_PUBLIC_SELECT = {"`, `app/api/webhooks/route.ts:107-109#"select: WEBHOOK_PUBLIC_SELECT,"`, `app/api/webhooks/[id]/route.ts:60#"select: WEBHOOK_PUBLIC_SELECT,"`), so the secret goes in on create and is never shown back; the settings page reloads the list after creating and never reads the `POST` response. `GET /api/slack` and `POST /api/slack` return the whole Slack configuration (`app/api/slack/route.ts:21-25#"return NextResponse.json({ config });"`, `app/api/slack/route.ts:93#"return NextResponse.json({ config });"`).

The PR-scan webhook secret is sealed because HMAC verification needs the plaintext, so it cannot be hashed (`lib/pr/webhook-secret.ts:6#"so it cannot be hashed"`). The key is derived with HKDF-SHA256 from `WEBHOOK_SECRET_KEY`, or from `NEXTAUTH_SECRET` when that is unset or blank (`lib/pr/webhook-secret.ts:32-37#"return Buffer.from(hkdfSync('sha256', material, KEY_SALT, KEY_INFO, 32));"`), and the row id is bound in as additional authenticated data (`lib/pr/webhook-secret.ts:45-57#"].join('.');"`). Opening returns `null` instead of throwing for a malformed value, a value sealed for another row, or a changed key (`lib/pr/webhook-secret.ts:65-79#"return plain === '' ? null : plain;"`), and the webhook route counts such a row as not verifying (`app/api/webhooks/github/route.ts:374-379#"if (secret && verifyGitHubSignature(rawBody, signature, secret)) verified.push(candidate);"`).

## Outgoing URLs

Outgoing webhook and Slack URLs are user input, checked twice by `lib/net/safe-fetch.ts`:

- **At save:** `POST /api/webhooks` and `POST /api/slack` call `assertPublicUrl` with `waitForSlot: false` and answer `400` on failure: a malformed or blocked URL carries its own message, a host whose lookup missed its bound answers `Host did not resolve in time`, and a check refused because the host name lookup cap is full answers `Too many host checks in progress, try again` (`app/api/webhooks/route.ts:77-89#"return NextResponse.json({ error: 'Invalid URL format' }, { status: 400 });"`, `app/api/slack/route.ts:53-65#"return NextResponse.json({ error: 'Invalid webhookUrl format' }, { status: 400 });"`). It accepts only `http:` and `https:` (`lib/net/safe-fetch.ts:395-397#"throw new SsrfBlockedError('Only http(s) URLs are allowed');"`), requires every resolved address to be public (`lib/net/safe-fetch.ts:517-523#"return { url, addresses: resolved };"`), against the blocked IPv4 ranges (`lib/net/safe-fetch.ts:59-69#"inRange('240.0.0.0/4') // reserved"`) and the blocked IPv6 ranges, judged on the address expanded to its eight 16-bit words (`::/96`, `::ffff:0:0/96` by its embedded IPv4, `2002::/16`, `2001:0000::/32`, `fc00::/7`, `fe80::/10`; an address that does not parse is blocked) so that every spelling of one address gets the same verdict (`lib/net/safe-fetch.ts:124-150#"if ((w0 & 0xffc0) === 0xfe80) return true; // link-local fe80::/10"`).
- **At delivery:** both deliveries go through `safeFetch` (`lib/alerts/notifier.ts:82#"{ dnsOwner: userId }"`, `lib/alerts/notifier.ts:155#"const res = await safeFetch("`), which repeats the check with `waitForSlot: true`, connects only to the addresses it validated (`lib/net/safe-fetch.ts:663#"lookup: pinnedLookup(addresses),"`, `lib/net/safe-fetch.ts:541-544#"const safe = validated.filter((a) => !isBlockedIp(a));"`) and does not follow redirects (`lib/net/safe-fetch.ts:692-693#"into an internal target."`). The delivery is also bounded, because the receiver is user-controlled: a response body over 1 MiB or a request (connect, headers and body together) that takes longer than 15 seconds destroys the socket and rejects with `SafeFetchLimitError` (`lib/net/safe-fetch.ts:565-566#"export const SAFE_FETCH_TIMEOUT_MS = 15_000;"`), which both deliveries return as `ok: false` like any other failed delivery and log with `console.warn`, carrying only the destination host and the error kind: the URL path of a Slack endpoint (or a webhook with a token in its path) is itself a secret, so it never reaches the log (`lib/alerts/notifier.ts:349#"console.warn("`), and the logged kind distinguishes the limit cases (`timeout`, `dns_busy`, `response_too_large`) from `ssrf_blocked` and plain errors. The host name lookup counts against the same 15 seconds: it is raced against that bound (`lib/net/safe-fetch.ts:501#"const records = await Promise.race([lookup, timeout]);"`) and the request timer only gets what is left (`lib/net/safe-fetch.ts:627#"const requestTimeoutMs = Math.max(1, timeoutMs - (Date.now() - startedAt));"`), so a resolver that never answers rejects with the same `SafeFetchLimitError` (kind `timeout`), and a late lookup answer is dropped: nothing dials on it. `dns.lookup` is kept, so `/etc/hosts` and nsswitch still apply; the race frees the delivery, not the libuv thread, which stays occupied until the system resolver gives up. The number of such occupied threads is bounded by a process-wide cap: the counter and the wait queue live on `globalThis` under one shared symbol (`lib/net/safe-fetch.ts:221-225#"const DNS_LOOKUP_STATE_KEY = Symbol.for('depsight.safeFetch.dnsLookups');"`), so the app server and the separately bundled cron path of the production build share one cap. A user-host lookup takes one of at most `MAX_CONCURRENT_DNS_LOOKUPS` (2, below the default pool of 4) slots (`lib/net/safe-fetch.ts:162-202#"export const MAX_CONCURRENT_DNS_LOOKUPS = 2;"`) and releases it only when the lookup itself settles, not when the bound fires, and a release with waiters hands the slot to a waiter instead of freeing it: the first whose owner is under its limit and who is not of the releasing owner, else the first in FIFO order (`lib/net/safe-fetch.ts:469-473#"next.grant();"`). A delivery names its user as the owner of its lookup (`dnsOwner` in the limits of `safeFetch`, passed by both deliveries of `lib/alerts/notifier.ts`), and one owner holds at most `MAX_CONCURRENT_DNS_LOOKUPS_PER_OWNER` (1) of the slots (`lib/net/safe-fetch.ts:208#"export const MAX_CONCURRENT_DNS_LOOKUPS_PER_OWNER = 1;"`), counted across every concurrent `notifyForScan` and `notifyScanCompleted` of that user: a user whose hosts park their lookups cannot take both slots, and the owner's further deliveries wait in the same queue, where it holds at most `MAX_QUEUED_DNS_LOOKUPS_PER_OWNER` (32) of the 64 places (`lib/net/safe-fetch.ts:219#"export const MAX_QUEUED_DNS_LOOKUPS_PER_OWNER = 32;"`): a delivery of that owner beyond its share is refused with kind `dns_busy` like a full queue, so one user cannot fill the queue, while a user with more than 33 deliveries waiting at once in this process loses the excess. While only one user parks its lookups, other users' deliveries find a slot or a queue place, and if the other slot is held by a third user they wait for it within their budget; two or more users at their share (2 x 32 = 64) can still fill the queue while holding both slots, and other users' deliveries are then refused with kind `dns_busy`. A lookup without an owner (the save routes) is bound by the global cap only. What a full cap does depends on the stated mode: the save routes are refused at once with kind `dns_busy`, before `dns.lookup` is called (`lib/net/safe-fetch.ts:447-452#"Already ${MAX_CONCURRENT_DNS_LOOKUPS} host name lookups in flight"`), while a delivery waits in the FIFO queue, its wait counting against its own 15 second budget, and one that cannot get a slot within it rejects with kind `timeout`; the queue holds at most `MAX_QUEUED_DNS_LOOKUPS` (64) waiters and a further one rejects with kind `dns_busy` (`lib/net/safe-fetch.ts:322-326#"Already ${MAX_QUEUED_DNS_LOOKUPS} host name lookups queued"`), and a waiter that timed out removes itself from the queue (`lib/net/safe-fetch.ts:336-339#"state.queued.splice(at, 1);"`), so a later release cannot hand it a slot. The same bound and the same process-wide counter apply to the check at save; only the mode (refuse versus wait) differs.

`PATCH /api/webhooks/[id]` changes only the `enabled` flag, so a stored webhook URL is never replaced without the save-time check.

## Dev Login

The GitHub provider is registered only when its client id and secret are set (`lib/auth.ts:11#"if (process.env.GITHUB_CLIENT_ID && process.env.GITHUB_CLIENT_SECRET) {"`), and the `dev-login` credentials provider only when `NODE_ENV` is `development` (`lib/auth.ts:25-45#"githubToken: 'dev-token',"`). Dev Login accepts any username without a password and creates a user with GitHub id `dev-<username>`, login `<username>` and the placeholder GitHub token `dev-token`.
