# API reference

All endpoints except `GET /api/health`, the NextAuth sign-in handlers under `/api/auth/*` and the GitHub webhook `POST /api/webhooks/github` (authenticated by its per-repository HMAC signature, see [GitHub pull-request webhook](#github-pull-request-webhook)) require authentication. Which credentials an endpoint accepts depends on the route:

- **Session or Bearer token:** `/api/scan`, `/api/license`, `/api/deps`, `/api/history`, `/api/overview`, `/api/sbom`, `/api/repos`, `/api/repos/tracked-ids`, `/api/policies`, `/api/policies/[id]`, `/api/policies/evaluate`, `/api/advisory-state`, `/api/ci/analytics/*` and `/api/ci/sync` accept either a NextAuth session (the dashboard) or an `Authorization: Bearer dsat_...` API token (headless agents such as the MCP server).
- **Session only:** `/api/export`, `/api/repos/sync`, `/api/dependabot`, `/api/dependabot/check`, `/api/dependabot/enable-all`, `/api/pr-scan`, `/api/me`, `/api/tokens` and `/api/tokens/[id]`, `/api/webhooks` and `/api/webhooks/[id]`, `/api/webhook-secrets` and `/api/webhook-secrets/[repoId]`, and `/api/slack` reject a Bearer token with 401. Token management is session-only on purpose: a `dsat_` token can never mint, list, or revoke tokens.

A Bearer `dsat_` token carries a `READ` or `WRITE` scope (`POST /api/tokens` accepts an optional `scope` body field, defaulting to `WRITE`); a `READ` token gets 403 on `POST /api/policies`, `PUT`/`DELETE /api/policies/[id]`, `POST /api/ci/sync`, `PUT`/`DELETE /api/advisory-state`, and the three scan-triggering POSTs (`/api/scan`, `/api/license`, `/api/deps`); all other Bearer-capable endpoints work with either scope. A session always has full access.

A session counts only when it carries a user id: a signed-in session whose user row no longer exists has none and is treated as no session (401 on every session-only route, and a Bearer token is then tried on the routes that accept one).

This table is a curated subset; the app exposes more route handlers (e.g. `/api/me`, `/api/tokens`, `/api/webhooks`, `/api/slack`, `/api/history`, `/api/overview`, `/api/pr-scan`, `/api/ci/analytics/*`) than are listed here.

| Method | Endpoint | Description |
|--------|----------|-------------|
| `POST` | `/api/scan` | Trigger CVE scan for a repository (body: `{ repoId }`); the answer carries `degradedReason`, null unless a source could not be read; rate limited, see [Rate limits](#rate-limits) |

Session or `WRITE` Bearer token |
| `DELETE` | `/api/advisory-state` | Clear the state of one finding, it is open again (body: `{ repoId, ghsaId, packageName }`). Idempotent. Session or `WRITE` Bearer token |

## Rate limits

`POST /api/scan`, `POST /api/license`, `POST /api/deps`, `POST /api/ci/sync` and `GET /api/repos` spend the owner's GitHub API quota, so they are limited per user, for a browser session and a `WRITE` Bearer token alike (a `READ` Bearer token too on `GET /api/repos`: a token of either scope spends its owner's GitHub quota there; the limit follows the user the credential resolves to, so several tokens of one user share it). The limit is a fixed one-hour window per user:

| Endpoint | Limit per user and hour |
|----------|-------------------------|
| `POST /api/scan` | 300 |
| `POST /api/license` | 300 |
| `POST /api/deps` | 300 |
| `GET /api/repos` | 300 |
| `POST /api/ci/sync` with a `repoId` | 300 |
| `POST /api/ci/sync` without a `repoId` (30-day sync of every tracked repo) | 12 |

Over the limit the endpoint answers `429` with a `Retry-After` header (whole seconds until the window resets) and a body `{ "error": "Rate limit exceeded", "retryAfterSeconds": <n> }`; no scan, sync or repository listing is started. A request that fails authentication (401) or the write-scope check (403) does not count; every other answer counts, including a 400 for a missing `repoId` and, on `/api/deps`, a 404 for a repository the caller does not own. Every row of the table is its own budget. One `GET /api/repos` call costs ceil(N/100) GitHub requests for N visible repositories, so the limit counts calls, not GitHub requests. The counters live in the app process, which matches the single-instance deployment (one `app` service); behind several instances each instance would enforce the limit separately. The 300 per hour limits sit above the dashboard's "scan all" run for an account with up to 300 tracked repositories (it calls scan, license and deps once per repository, so each endpoint sees at most 300 calls) and above a CI job that syncs one repository after every push (`/api/ci/sync` with a `repoId`).

## GitHub pull-request webhook

`POST /api/webhooks/github` takes GitHub's `pull_request` webhook and runs the same scan as `POST /api/pr-scan`. Setup (secret, payload URL, events) is in [docs/configuration.md](configuration.md#pr-scan-webhook-optional). It has no session and no Bearer token: the only authentication is the HMAC-SHA256 of the raw request body, sent as `X-Hub-Signature-256: sha256=<hex>` and compared in constant time, under the webhook secret of a user who tracks the repository the payload names. The endpoint is on whenever sealing key material exists unless the operator sets `GITHUB_WEBHOOK_DISABLED=true` (then it answers `404` before reading the request), and because the secret belongs to the tracking row it does a database lookup of the repository named by the payload before the signature is verified (an indexed lookup of at most 25 rows). Without key material it answers `503`: `WEBHOOK_SECRET_KEY` or `NEXTAUTH_SECRET` is needed, and a deployment that sets only `AUTH_SECRET` has neither. A stored secret that no longer opens is logged once per process by row id, and the instance-wide `GITHUB_WEBHOOK_SECRET` is ignored with a one-time warning at the first delivery.

**Secrets.** Each tracked repository row carries its own secret, minted and rotated by its owner (session only):

| Method and path | Purpose |
|-----------------|---------|
| `GET /api/webhook-secrets` | `available` (key material for sealing is present, the same condition under which minting does not answer `503`) and the caller's tracked repositories with `configured` (a secret is stored), `usable` (it also opens under the current key material; false for a configured secret sealed under other key material or damaged, which never verifies a delivery and must be rotated), `rotatedAt` and `scanForks` (the row's own fork setting: `true`, `false` or `null` for the instance default), `private` (the stored visibility, refreshed by signed webhook deliveries and by sync, which the settings page uses to show that the opt-in is ignored on a public repository), plus `scanForksDefault` (whether `GITHUB_WEBHOOK_SCAN_FORKS` is `true`); never the secret |
| `POST /api/webhook-secrets/[repoId]` | Mint the secret, or rotate it (the old one stops verifying at once). The response `{ secret, rotatedAt, repository }` is the only time the plaintext is shown (`Cache-Control: no-store`). `404` for a repository the caller does not own, `409` for an untracked one, `503` without sealing key material, `429` over 60 calls per hour |
| `DELETE /api/webhook-secrets/[repoId]` | Remove the secret; `404` for a repository the caller does not own |
| `PATCH /api/webhook-secrets/[repoId]` | Body `{ "scanForks": true \| false \| null }`: whether the webhook scans fork pull requests for this tracked repository of the caller; `null` clears the setting so the row follows `GITHUB_WEBHOOK_SCAN_FORKS`. Answers `{ success, scanForks }`; `400` for any other body, `404` for a repository the caller does not own or that is not tracked |

**Trust model.** depsight looks up the tracked repositories named by the payload (`repository.owner.login`, `repository.name`) that have a secret, tries the signature against each candidate's secret (at most 25 rows, constant-time compare, no early exit), and acts only for the row whose secret verifies, with that user's GitHub token. A secret therefore only ever authorises scans of its own repository under its own owner: when users A and B both track a repository, a delivery signed with B's secret scans under B and never under A, and B's secret signed over a payload naming a repository only A tracks verifies against nothing. There is no instance-wide secret. Unsigned, wrongly signed, unknown-repository, untracked-repository and no-secret deliveries all get the same `401`, so the status and body do not reveal which repositories are tracked. The response time can still differ: a delivery for a tracked repository costs one HMAC per candidate row, an unknown one costs a single HMAC, so a caller measuring latency can tell a tracked repository from an untracked one (a residual; the 401 itself says nothing). On a public repository the comment is public, and GitHub sends the `opened` and `synchronize` deliveries for fork pull requests too, so depsight ignores them (200) unless the verified repository is private and its row's owner opted in with `PATCH /api/webhook-secrets/[repoId]` or, for a row without a setting, `GITHUB_WEBHOOK_SCAN_FORKS=true` is set. The per-repository opt-in is ignored for a public repository (an explicit opt-out still holds; the instance default alone then decides). Visibility is judged from each delivery's payload (`repository.private` and `repository.visibility`), not from the stored flag, so a private repository that becomes public stops scanning forks with its next delivery; a payload without a clear visibility, or whose two fields disagree, counts as public, and an `internal` repository counts as private. The same verified delivery also refreshes the stored `private` flag of the row that verified it when the payload clearly states a different visibility (a missing, mistyped or contradictory payload never writes; an unverified or unmatched delivery never writes; a failed write is logged and does not change the answer), so `GET /api/webhook-secrets` and the settings page converge on the first signed delivery after a visibility change. Until then, or until the next sync, the stored flag can be stale: a repository that became public still shows Scan selectable although the server already ignores it, and one that became private shows Scan disabled (this fails safe). The setting is per tracking row: when several users track one GitHub repository, each row decides for itself, only the row whose secret verified the delivery is consulted, and one user's opt-in never makes depsight scan a fork pull request for another user's row. The fork check runs after the signature check (only a caller holding a valid secret ever sees that answer) and before the replay guard and the rate limiters (a fork delivery spends no scan budget).

| Status | When |
|--------|------|
| `202` | Verified `opened` or `synchronize` delivery from a pull request in the same repository (or from a fork when the repository is private and the verified row opted in, or when the row has no setting, or opted in on a public repository where the opt-in is ignored, and `GITHUB_WEBHOOK_SCAN_FORKS=true`); the scan runs in the background (GitHub allows a delivery 10 seconds) |
| `200` | Verified delivery that is ignored: a `ping`, any other event, any other action (including `reopened`), a pull request from a fork (unless the repository is private and the verified row opted in, or `GITHUB_WEBHOOK_SCAN_FORKS=true` applies to the row; a deleted fork with a null head repository counts as a fork, compared case-insensitively), or a replayed delivery |
| `400` | Verified delivery with an invalid pull request number or a missing or malformed `X-GitHub-Delivery` header |
| `401` | Nothing verified: missing, malformed or wrong signature (wrong length included), a body that is not JSON or names no valid repository, a repository that is not tracked or has no secret |
| `413` | Body over 1 MiB, rejected without buffering the rest |
| `404` | `GITHUB_WEBHOOK_DISABLED=true`: the endpoint is switched off and the body is not read |
| `429` | Rate limit, with a `Retry-After` header: the pre-verification limit (per client address, endpoint-wide, or the separate budget of GitHub's hook addresses; the body is not read) or one of the post-verification budgets below |
| `503` | No sealing key material (`WEBHOOK_SECRET_KEY` and `NEXTAUTH_SECRET` both unset or blank): the endpoint is disabled and scans nothing |

Only the PR number, action and head repository name of a verified payload are used (and the owner and repository name for the lookup); no URL from the payload is ever fetched. The scan uses the repository, owner and GitHub token of the verified row.

**Replay protection.** A delivery is remembered for 24 hours under its `X-GitHub-Delivery` id and, because that header is not covered by the signature, also under the SHA-256 of its body; a second delivery with either key for the same tracking row is answered `200` and ignored. The keys are scoped to the verified row, so one user cannot make another user's delivery look like a duplicate. A delivery whose scan fails is forgotten again so GitHub can redeliver it. The memory is bounded (150 000 keys, roughly 25 MB at the cap, which is two keys for each of the 3000 deliveries per hour the endpoint-wide ceiling admits, over the 25 fixed hourly windows a 24-hour memory can span; oldest dropped first) and lives in the app process: a restart clears it, and several instances would each keep their own, which matches the single-instance deployment. The cost of a miss is one repeated scan that rewrites the same PR comment, bounded by the rate limit.

**Rate limit.** Only a delivery verified against a tracked row, and not ignored as a fork, counts: 60 per tracking row (one budget per user and repository) and hour, 120 per hour for all of one user's rows together, and 3000 per hour for the whole endpoint (fixed windows, in the app process like the limits above). Rejected and ignored deliveries do not count. The scans a delivery starts spend the tracking user's own GitHub quota, which the per-row and per-user budgets already bound; the endpoint-wide figure is a ceiling that protects the server, not a scan budget. The ceiling bounds accepted deliveries (each starts a background PR scan and adds two replay-guard keys, which is where the roughly 25 MB at the cap comes from), not verification CPU: signature verification is bounded by the pre-verification limits below, not by this ceiling. It costs one JSON parse of up to 1 MiB plus up to 25 HMACs; measured on one machine, a crafted 1 MiB body (many short keys, tiny objects or deeply nested arrays) parses in roughly 10 to 30 ms (a typical payload in under 2 ms) and an HMAC costs about 0.35 ms per candidate per MiB. On an instance with open sign-in, enough accounts that each track a repository and mint a secret can still use up that ceiling together and make other users' deliveries answer `429` for the rest of the hour (a residual; the operator can restrict who may sign in). Without a well-formed signature a request costs one capped read, and with one it costs one JSON parse, one indexed lookup and at most 25 HMACs; the next paragraph bounds how many of either an unauthenticated caller can send.

**Pre-verification limits.** Before the body is read, parsed or hashed, every request counts against two fixed one-minute windows: 60 per client address and then one shared budget, 600 for the whole endpoint, or 300 when the client address is one of GitHub's hook addresses (see *GitHub's hook addresses* below). The address check comes first, so a request refused for its address spends neither shared budget. Over either one the answer is `429` with `Retry-After`, and the body is not read. Verified, unsigned and badly signed requests all count, and a request refused with `404` (switched off) or `503` (no key material) does not. Legitimate traffic is a few deliveries a minute from GitHub's hook addresses, well below both figures. The windows live in the app process, like the other limits.

*Which address.* Node gives a route handler no socket address, so the client address comes from `X-Forwarded-For`, and only from the hop a trusted reverse proxy appended: entries are counted from the right, and with `WEBHOOK_TRUSTED_PROXY_HOPS` proxies in front of the app (default `1`, the traefik of the production deployment, which is the only way to reach the app there) the Nth entry from the right is the client. Entries to its left are whatever the caller wrote and are never used, so a caller behind the proxy cannot get a fresh bucket by sending its own `X-Forwarded-For`. Next.js fills a missing `X-Forwarded-For` with the socket peer before the handler runs, so a request without the header is keyed on that peer. The `unknown` bucket (60 per minute, shared) collects requests whose trusted entry is missing (fewer entries than trusted proxies) or is not a plain IP address (an IPv6 zone id such as `%eth0`, or anything longer than 45 characters, counts as not plain, so a caller cannot put long text into the limiter key). `WEBHOOK_TRUSTED_PROXY_HOPS=0` ignores the header altogether, which is right when the app is reached without a proxy: every caller then shares that one bucket, so a direct deployment is limited as a whole, not per client. With `0` no request is classified as coming from a GitHub hook address either: the `unknown` address is not an address, nothing is fetched from `api.github.com`, and every caller (a hook address written into `X-Forwarded-For` included) shares the `unknown` bucket and the endpoint-wide ceiling. A value that is not a whole number from 0 to 8 is replaced by `1` with a one-time warning.

*What still holds when the header cannot be trusted.* If the app is reachable without the proxy (for example through the published port of `docker-compose.yml`, or a proxy that does not set the header), a caller can write the trusted entry itself and get a new bucket per request. A caller that can write the trusted entry can also write a hook address into it, which moves its requests to the budget of GitHub's hook addresses (below) instead of the ceiling, so it can spend both. The bounds that remain are the two shared budgets together, 600 for the endpoint-wide ceiling plus 300 for the hook budget, which cap the pre-verification work at 900 requests a minute (at up to about 40 ms per request, the measured 10 to 30 ms to parse a crafted 1 MiB body plus up to about 9 ms for 25 HMACs, roughly 36 CPU-seconds a minute at most; the ceiling alone is 600 times 40 ms, roughly 25), the two per-address tables (one for hook addresses, one for all others), which each hold at most 10 000 windows (further addresses share one overflow bucket per table), and the request body cap of 1 MiB. The cost of that bound is availability: a caller who spoofs addresses can spend the endpoint-wide figure, and the hook budget too by claiming hook addresses, and make GitHub's deliveries answer `429` for the rest of the minute (a residual; GitHub redelivers on demand, and an operator exposed this way can set `GITHUB_WEBHOOK_DISABLED=true` or restrict the port to the proxy).

*Lost deliveries behind the proxy.* The endpoint-wide figure can be spent honestly: behind traefik a caller with ten or more source addresses can send 60 empty-body requests a minute from each, reach 600 together and make every request from a non-GitHub address answer `429` for the rest of the minute. GitHub does not redeliver a failed webhook by itself (a delivery has to be redelivered by hand or through the API from the repository's webhook settings), so a delivery refused that way is lost until someone redelivers it. The separate budget below keeps real deliveries out of that for callers the trusted hop places outside GitHub's ranges, who cannot spend it. The first request the ceiling refuses in each window writes one warning to the server log (`PR scan webhook: the endpoint-wide pre-verification limit ... was reached`), so an operator can see that requests were refused.

*GitHub's hook addresses.* A request whose trusted client address (the one chosen by the rule above, never an entry to its left) lies in the `hooks` ranges that GitHub publishes at `https://api.github.com/meta` (IPv4 and IPv6; an IPv4-mapped IPv6 address counts as the IPv4 address it wraps) is counted against a budget of its own, 300 a minute shared by all such addresses, and not against the 600 of the endpoint-wide ceiling. The classification happens before the per-address check: a hook address has its own per-address window of 60 a minute, in a table of its own (10 000 windows at most, like the general one) that only requests classified as hook addresses write to. Because the classification rests on the trusted hop (below), traffic that reaches the app through the proxy from other addresses cannot fill that table, cannot push a hook address into an overflow bucket, and cannot spend the 300. Requests from hook addresses do not count against the ceiling, so, on the same basis, a caller who exhausts the ceiling, or fills the general per-address table, does not refuse a real delivery. The budget bounds the same pre-verification work as the ceiling, so the worst case is the two figures together, 900 requests a minute (about 36 CPU-seconds at the per-request cost given above). The first request refused over it in each window writes one warning to the server log (`PR scan webhook: the pre-verification limit for GitHub's hook addresses ... was reached`). Properties that matter when relying on it:

- It rests on the trusted hop. The classification uses only the address `X-Forwarded-For` yields under `WEBHOOK_TRUSTED_PROXY_HOPS`; a hook address written into an entry to its left changes nothing. When the app is reachable without the proxy, a caller can write the trusted entry itself and claim a hook address, which moves its traffic to the 300 budget rather than the 600 one and takes real deliveries with it, just as spoofing already does for the ceiling. With `WEBHOOK_TRUSTED_PROXY_HOPS=0` the header is not read at all: no request is classified as a hook address, nothing is fetched, and all callers share the `unknown` address and the ceiling.
- It separates GitHub's infrastructure from other sources, not this instance's deliveries from everyone else's. Deliveries that any GitHub user points at this URL (for another repository, or with a wrong secret) also come from these ranges and share the hook budget and its 60-a-minute-per-address windows, so they can spend them like a real delivery can.
- The ranges are fetched lazily and cached in the app process: nothing is fetched at start-up, the first request that carries an address starts one background fetch (it does not wait for it and is counted against the ceiling), at most one fetch runs at a time with a 5-second timeout, and the cache is refreshed when it is an hour old. A fetch that fails is retried no sooner than five minutes later (one warning is logged per run of failures), and ranges that could not be refreshed for 24 hours are dropped. The response is read with a cap of 2 MiB (refused when `Content-Length` declares more, and cancelled as soon as more has arrived) before it is parsed, and an entry wider than an IPv4 /8 or an IPv6 /16 is dropped as implausible, so a `0.0.0.0/0` in the answer cannot put every address in the hook class. The app needs outbound HTTPS to `api.github.com` for this.
- Every failure ends in the single ceiling. Before the first successful fetch, after a failed one, for a response without a usable `hooks` list, and once stale ranges are dropped, every request is counted against the endpoint-wide ceiling exactly as if the budget did not exist, so the residual described above applies again until a fetch succeeds.
- A deployment whose webhooks do not come from github.com (GitHub Enterprise Server) has no matching public ranges; its deliveries stay on the ceiling.

## MCP server

For agent access, depsight ships an MCP server in [`mcp/`](../mcp/README.md) that exposes queries (CVEs, licenses, deps, policies, CI analytics), SBOM export, and a scan-trigger tool to Claude and other MCP-capable clients; read-only apart from the scan trigger.
